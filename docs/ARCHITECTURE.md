# Architecture

## Modules

```text
src/
├── problem/
│   ├── scenario/
│   └── constraints/
├── csp/
│   ├── model/
│   ├── solver/
│   └── heuristics/
├── optimisation/
│   └── hillClimbing/
├── energy/
│   ├── calculator/
│   └── objective/
├── visualisation/
│   ├── searchTree/
│   ├── backtracking/
│   ├── hillClimbing/
│   └── events/
└── interface/
    ├── input/
    └── output/
```

| Directory | Responsibility |
| --- | --- |
| `problem/` | Stores real-world scenario facts and rules. It does not implement the CSP solver or own the solver-ready CSP representation. |
| `problem/scenario/` | Represents generic building, room, device, occupancy, environmental, and user-requirement input. Building type is input data, not an application mode. |
| `problem/constraints/` | Represents domain-specific rules and scenario-level constraints before CSP adaptation. |
| `csp/model/` | Converts or represents `problem/` data as the solver-ready CSP and owns variables, domains, assignments, and solver-ready constraints. |
| `csp/solver/` | Implements CSP solving with backtracking and emits CSP execution events. |
| `csp/heuristics/` | Implements MRV, Degree Heuristic, LCV, Forward Checking, and Constraint Propagation as appropriate. |
| `optimisation/hillClimbing/` | Implements Simple Hill Climbing and generates feasible neighbours. It uses `energy/` for evaluation and must not duplicate energy calculations. |
| `energy/calculator/` | Performs device and total energy-consumption calculations and configuration comparisons. |
| `energy/objective/` | Defines and evaluates the optimisation objective using the energy-calculation module. |
| `visualisation/` | Visualises only actual events and data generated by the AI modules; it must never implement a second CSP solver or Hill Climbing algorithm. |
| `visualisation/searchTree/` | Renders the actual CSP solver execution tree, including real branches and backtracking. |
| `visualisation/backtracking/` | Presents actual partial assignments, constraint failures, forward-checking effects, and backtracking events. |
| `visualisation/hillClimbing/` | Presents actual hill-climbing iterations, neighbours, accepted moves, and termination. |
| `visualisation/events/` | Adapts and presents solver and optimisation events without recreating algorithm logic. |
| `interface/input/` | Handles generic scenario input and algorithm start actions. |
| `interface/output/` | Presents final results and connects algorithm execution to the lightweight UI. It contains no AI logic. |

## Data flow

`Input → Problem Model → CSP Model → CSP Solver → Feasible Configuration → Hill Climbing → Energy Evaluation → Result → Visualisation`

## Execution events

The CSP solver emits events such as:

- `VARIABLE_SELECTED`
- `VALUE_TRIED`
- `CONSTRAINT_CHECKED`
- `CONSTRAINT_FAILED`
- `FORWARD_CHECK`
- `BACKTRACK`
- `SOLUTION_FOUND`

Hill Climbing emits events such as:

- `INITIAL_STATE`
- `NEIGHBOUR_EVALUATED`
- `MOVE_ACCEPTED`
- `NO_BETTER_NEIGHBOUR`
- `OPTIMUM_FOUND`

The visualisation layer consumes these events and associated state. It must never recreate the algorithms internally or invent their execution. Search-tree visualisation must represent the CSP solver's actual execution; it must not fake branches, backtracking, constraint failures, or results.
